Introduction — what this drone is supposed to do

Fly point A to point B with no GPS, self-localizing and mapping from camera and inertial data alone. That's the destination architecture below, and the code for all of it exists and runs. It is not, however, what any flight documented in this record actually flew on — every flight so far has PX4's own GPS-fused pose feeding control, mapping, and planning, deliberately, as a Milestone-1 stepping stone (§08, §02). cuVSLAM runs the whole time in parallel, tracked and logged, but not yet wired into the loop that matters.

Localization
cuVSLAM
Stereo IR + IMU → 6-DOF pose. Destination path: feeds EKF2 as external vision, no GPS anywhere. Current status: runs standalone, tracked but not fused (EKF2_EV_CTRL 0) — see §02.
Estimation
EKF2
PX4's own estimator. Destination path: fuses cuVSLAM's vision pose. Currently fuses GPS instead — same estimator, different aiding source.
Mapping
nvblox
Depth + pose → an ESDF (distance field). Raw material for avoidance, not avoidance itself.
Planning
Fast-Planner
Consumes the ESDF via get_esdf_and_gradient, produces a collision-free trajectory.
Control
PX4
Blind to obstacles. Tracks whatever setpoints the bridge hands it, nothing more.

Two constraints shape everything below. First, the occlusion theorem: a goal sitting behind an obstacle is unobservable at the moment the mission is triggered, which makes receding-horizon planning — plan to the frontier of what's actually been seen, fly, observe more, replan — mandatory rather than a nicety. Second, controllable safety: on real hardware, a drone that loses control is not a failed test run, it's broken hardware or an injury, so the kill path (graceful and emergency) and the killswitch envelope get the same engineering attention as the flight stack itself.

Audited 2026-08-28: this document previously overstated how GPS-free the current setup is — it read as though the destination architecture (above) were what every flight actually flew on. It wasn't. Checked directly against the running code (the airframe file's EKF2_EV_CTRL 0, ground_truth_tf.py's own docstring, ARCHITECTURE.md's Milestone split) and corrected in §00, §02, and §39 to say plainly: every flight in this record flew on PX4's GPS-fused pose, by deliberate design, not on cuVSLAM. No system or code behavior changed — this was a documentation correction only.

Executive Summary — status at a glance

Everything below this point is detail. This is the summary a reader can stop at.

Solid

  • B reached, with the real 8-pillar obstacle ring between start and goal, ten separate times across the second half of this record — the fastest at 2.15s, with Gazebo's own GUI left running the whole time — not a one-off, a repeatable outcome.
  • The thrust-authority limit found in §23 is closed: a combined thrust-vector budget (search pruning, an exact closed-form reallocation ratio, and an optimizer cost term, all sharing one physically-derived 12.5 m·s⁻² ceiling) replaced independent per-axis limits that were letting trajectories ask for more than the airframe could give.
  • Obstacle detection is now provable, not inferred: a dedicated camera-verified signal (observed and occupied, not merely "not yet seen") renders as a tight cluster exactly where the real pillar is, growing live as the drone approaches it.
  • The planner's single-ray blind spot — the actual reason B kept going unreached — found and fixed: a fan of candidate detour angles now tried whenever the straight line to the goal is blocked.
  • An executor-stall guard closes a real, load-triggered crash mechanism: validated across 200+ genuine multi-second stalls with zero crashes since.
  • An odom-staleness guard (§31) closes a second, distinct crash mechanism — a stalled position-data source could pin a safety hold to a phantom location; caught it happening live twice, fixed, then watched it correctly refuse to act on stale data the next time the same underlying stall recurred.
  • Two real, measured cost reductions (§34) target the actual Jetson deployment, not just tonight's dev box: unwatched visualization publishers now skip their work entirely (2 of 5 had zero real consumers, ever), and the corridor ESDF fetch — the single most expensive required callback in the system — dropped 40–45% (184–232ms → 104–120ms) from a correctness-preserving algebraic hoist.
  • Killswitch envelope: four independent bounds, 12–55ms breach-to-disarm latency, all four confirmed firing live, including twice as the sole reason a real divergence didn't become a real crash.
  • EKF2 confirmed accurate to ≤0.27m against raw Gazebo ground truth during controlled flight — the estimate was never the problem.

Known limitation

  • Flights are safe under every load condition tested, but under sustained contention they can fully livelock — parked safely, but making zero progress, for as long as the load persists (44 minutes observed in one case, §32). This is the worst-case form of the "safe but slow" limitation, not a separate problem.
  • Root cause is architectural: the node is single-threaded, so the same guard that keeps every individual stall safe can, under sustained load, return early on every tick faster than it clears — starving the FSM's own replan-trigger logic indefinitely. A full container restart measurably helps (load 10+ → 3-5, zombies 77 → 2) but isn't sufficient on its own; the livelock recurred at merely moderate load on the very next re-test.
  • The structural fix — a multi-threaded executor splitting control and map work onto separate threads — was built and tested the same night (§33). It eliminated the livelock outright, but exposed an unsynchronized read/write race on the map's shared buffers that broke path search almost entirely. Reverted rather than ship a race condition on flight-safety code; the real fix needs proper synchronization added deliberately, not live.

Deferred debts

  • Container OOM recurs — confirmed repeatedly this session, not a one-time event — and takes the whole stack, safety mechanisms included, down with it. A restart recovers it in seconds with an operator present; there's no equivalent safety net for unattended hardware yet.
  • Gazebo's own GUI camera stopped responding to drag input on both a mouse and a touchpad, mid-session, with no root cause isolated remotely — worked around with a fixed camera_pose, not fixed.
  • Milestone 2 (cuVSLAM driving control) entirely deferred; a historical GPU-contention drift issue is why it's not driving control yet.
  • Isaac ROS 3.2 on the actual Jetson Orin Nano — not started.

Part I — System Architecture

Before the chronicle of what broke and what got fixed: what the system actually is. Six pieces, in the order data flows through them — camera and IMU in, a rotor command out. Written for a reader who wants the mechanism first and the incident history second.

§02Reference

Perception: the VIO path, and what's actually flying today

Mechanism

Everything downstream — the map, the plan, the control loop — is only as good as knowing where the drone actually is. The architecture below is designed to get that from a camera and an IMU alone. Every flight in this record so far got it from GPS instead — deliberately, and that's the first thing to understand about this section, not a footnote at the bottom of it.

Stereo visual-inertial odometry (cuVSLAM)

Two cameras (a fixed-baseline stereo pair) and an IMU feed cuVSLAM[2], an Isaac ROS GPU-accelerated VIO front end. Each frame, it tracks a set of visual features across the stereo pair and across time — the stereo baseline gives per-feature depth by triangulation, and tracking the same features frame-to-frame gives the camera's own motion. That visual estimate is tightly coupled with the IMU: the IMU is cheap and fast (hundreds of Hz) but drifts badly on its own; the camera is accurate but comparatively slow and can fail on textureless or fast-moving scenes. Fusing them gives a 6-DOF pose estimate that's both high-rate and drift-resistant — this is the GPS substitute the architecture is built around, and it's GPU work specifically so it can run in real time on the Jetson's own accelerators rather than starving its CPU cores. It runs, continuously, on every flight in this record. It just isn't what any of those flights flew on (below).

EKF2 — PX4's own state estimator, and what it's actually fusing right now

PX4 runs its own extended Kalman filter (EKF2) onboard. It predicts state forward continuously from raw IMU integration (fast, cheap, drifts alone) and corrects that prediction with an external position fix (slower, but bounds the drift). The architecture is built to supply that fix from cuVSLAM (EKF2_EV_CTRL nonzero, external vision). As configured for every flight in this record, it's supplied by GPS instead (EKF2_EV_CTRL 0, set in the airframe file, 4022_gz_x500_depth_stereo) — the exact same EKF2, the exact same downstream consumers, just a different aiding source feeding it. This isn't a display-only or map-centering substitution: it's the actual estimate PX4's own position/velocity controllers fly on, published as /fmu/out/vehicle_odometry and republished as /ground_truth/odom (§03) for nvblox's camera pose and Fast-Planner's sdf_map frame alike. GPS is genuinely load-bearing for control, mapping, and planning right now, not just one of the three.

Why, and what closes it

EKF2_EV_CTRL 0 wasn't the original plan — it was forced by a real incident (a Phase 6 flight test where cuVSLAM's tracking drifted ~55m from the Gazebo-confirmed position under GPU contention with nvblox's concurrent CUDA context, corrupting EKF2's fused estimate badly enough to cause a genuine runaway, stopped only by killing the node). ARCHITECTURE.md then formalized staying on GPS as a deliberate Milestone-1 choice, not just a leftover workaround: with pose held constant and known-reliable, a Milestone-1 failure has exactly one possible cause (the new nvblox/ESDF wiring), not two entangled ones. cuVSLAM's own accuracy is still real and separately measured — ≤0.27m against raw Gazebo truth during controlled flight (Reference table) — it just isn't the thing in the loop. Re-enabling EKF2_EV_CTRL and root-causing the GPU-contention drift is Milestone 2, not started (Open issues).

§03Reference

Mapping: depth images to a safety field

Mechanism

The planner never looks at a depth image directly. Everything it knows about the world comes through one number per voxel: distance to the nearest obstacle.

Depth fusion (nvblox)

The D435i's depth stream (in SITL, Gazebo's[6] simulated depth camera) feeds nvblox[3], which fuses each depth image into a voxelized TSDF — a truncated signed distance field. For every pixel with a valid depth reading, nvblox walks the ray from the camera out to that measured surface and updates a running signed-distance estimate in every voxel within a narrow band around the surface (positive in front of it, negative behind, zero at the surface itself) — the same integration scheme real-time depth-fusion systems have used since KinectFusion[7], GPU-accelerated so it can keep up with a live camera feed. Averaging many rays over time is what makes the fused surface far more stable than any single noisy depth frame. nvblox additionally propagates a full ESDF (a genuine distance-to-nearest-obstacle value at every voxel, not just the narrow near-surface band the TSDF tracks) out from that fused surface — that ESDF is the actual product this project consumes.

How Fast-Planner pulls from it

SDFMap never subscribes to raw depth or does its own raycasting — that code path exists in the source but is intentionally dead (see §25/§03's own comments in sdf_map.cpp). Instead it holds an async service client against /nvblox_node/get_esdf_and_gradient and pulls on two independent timers: a near tier (0.25s, ~226,981 voxels, close-range avoidance depends on this one being fresh) and a slower corridor tier (4.0s as of §30, ~2,146,689 voxels, longer-range look-ahead). Async, not blocking — a blocking call on a single-threaded executor would deadlock the node against its own thread.

The resolution mismatch, and why min-pooling

nvblox's own voxels (0.05m) are finer than Fast-Planner's grid (0.1m) — a real 2× mismatch, confirmed live rather than assumed. Each response is pooled down: for every destination voxel, onEsdfResponse() looks at the pool_factor³ (2×2×2 = 8) source voxels it covers and keeps the minimum signed distance among them, not an average or nearest-sample. Minimum is the conservative choice for a safety field — it never overstates clearance, so a destination voxel straddling an obstacle edge reads as closer to that obstacle than a softer statistic would suggest. (§34 hoisted the redundant address arithmetic out of this exact loop — same result, ~40-45% less time to compute it.)

Unknown space is occupied, not free

Every voxel starts (and stays, until actually observed) marked occupied — a deliberate policy flip made after a real incident where "unknown = free" let a trajectory fly straight through a real, simply-not-yet-seen obstacle. "Never plan through space not confirmed free" is the general rule every trajectory-generating code path obeys (the search's pruning, the frontier's ray march, the optimizer's cost term). The one narrow, deliberate exception is checkTrajCollision's watchdog on an already-committed trajectory, which requires actual observation before flagging new danger — specifically to avoid re-triggering the earlier false-collision-storm bug (Lỗi 1) on an already-in-flight path. It's a narrow carve-out for one already-safe case, not a general "unknown is fine" policy.

Where the map actually lives

Every visualization publisher (and, until §27's fix, every real avoidance-relevant buffer index) is bounded by local_bound_min_/local_bound_max_ — a moving 3D voxel-index window recentered on the drone's live position (camera_pos_ ± local_update_range_) every time the map actually updates. For the whole engagement before §27, nothing ever set this outside its C++ zero-default, so every map display was rendering one fixed, meaningless corner voxel regardless of where the drone actually was — a real bug, not a display quirk, fixed by recentering it inside onEsdfResponse().

§04Reference

Search: the kinodynamic planner

Mechanism

The map says where it's safe to be. The search's job is finding a path there the airframe can actually fly, not just a geometrically clear one.

Motion-primitive expansion, not a geometric graph

A plain shortest-path search over free-space cells would happily hand back a trajectory with instantaneous direction changes — geometrically valid, physically impossible for a quadrotor to track. Fast-Planner's[1] kinodynamic_astar instead expands the search from the vehicle's actual current state (position, velocity, acceleration) forward using discretized acceleration primitives integrated over a short time step — every expanded node is a state the vehicle could actually reach by commanding some feasible acceleration and coasting. The search explores outward from there, biased toward the goal by a standard admissible heuristic, exactly like A* over cells but with the state itself carrying real physics.

Two independent prunes, not one

Every candidate primitive is checked against two separate bounds before it's ever expanded further: collision (evaluateCoarseEDT → sdf_map_->getDistance() — reject anything that passes too close to an occupied or still-unknown voxel) and, since §24, thrust authority (reject any primitive whose combined ‖a_cmd + g·ẑ‖ exceeds the airframe's real, telemetry-measured ceiling of 12.5 m·s⁻²). Before §24 these were independent per-axis velocity/acceleration caps that could jointly ask for more thrust than the airframe could ever deliver, no matter how each looked in isolation — the combined check is what actually matches the physics of a single shared rotor budget.

Output

A coarse, discrete-time sequence of position/velocity/acceleration waypoints — dynamically plausible, provably collision-clear against the map as currently known, but not yet smooth. That's what gets handed to the optimizer next.

§05Reference

Trajectory: splines and optimization

Mechanism

The search finds a feasible route. The optimizer turns it into something the flight controller can actually track smoothly.

Why a B-spline

A uniform B-spline represents the whole trajectory with a small number of control points, and — critically — it's smooth by construction: position, velocity, and acceleration are just successive derivatives of the same underlying curve (velocity_traj_ = position_traj_.getDerivative(), and again for acceleration). Moving one control point reshapes the curve locally and smoothly rather than introducing a kink, which is exactly the property an optimizer needs to be able to refine a rough initial guess into something flyable without fighting discontinuities at every step.

What the optimizer actually minimizes

bspline_optimizer takes the search's coarse output as its starting guess and adjusts control points to minimize a weighted sum of costs: smoothness (penalize sharp curvature), collision (an ESDF-gradient term that pushes points away from nearby obstacles — the same distance field the search used, now driving a continuous gradient rather than a hard prune), dynamical feasibility (stay under velocity/acceleration bounds), and — since §24 — the same combined thrust-vector term the search prunes on, now expressed as a smooth, analytically-differentiable cost rather than a hard reject, so the continuous optimizer can't quietly reshape the search's already-thrust-valid output back past the limit.

Reallocating time when a bound is still violated

If the optimized spline still exceeds a dynamical bound afterward, reallocateTime() stretches the time allocated between the offending control points — effectively "take this segment slower" — via an exact closed-form quadratic solve (replacing an earlier approximation that measurably under-stretched, since it assumed a pure per-axis acceleration term with no fixed gravity-compensation offset). Each reallocation pass is capped per-interval by limit_ratio_ (1.1 → 1.3 after §24 — the single change that actually broke a persistent-rejection stall, more than the exact-math fix itself), and the whole reallocate-and-recheck loop is capped at 8 iterations (raised from 3), with an explicit reject-and-hold safety return if it's still infeasible after that — the planner refuses to hand back and fly a trajectory it can't make work, rather than committing to something marginal.

§06Reference

Execution: the FSM and the frontier

Mechanism

A finished trajectory doesn't fly itself. Something has to decide when to trust it, when to replan, and — because the goal can be behind an obstacle at trigger time — what to actually aim at along the way.

The state machine

KinoReplanFSM cycles through INIT → WAIT_TARGET → GEN_NEW_TRAJ → EXEC_TRAJ, with REPLAN_TRAJ re-entered whenever the currently-executing trajectory nears its own end (no_replan_thresh_/replan_thresh_) or gets explicitly retriggered. execFSMCallback(), on a 10ms timer, is the heartbeat that drives every transition; checkCollisionCallback(), on its own 50ms timer, runs independently alongside it watching for danger regardless of what state the FSM is in.

The receding-horizon frontier — why the target isn't always the real goal

The occlusion theorem this whole architecture is built around: a goal behind an obstacle is genuinely unobservable at the moment a mission is triggered, so committing straight to it isn't possible even in principle. computeFrontier() substitutes the true mission goal with whatever's actually reachable and confirmed-free right now — a straight ray-march toward the goal, falling back to a fan of yaw-rotated candidate rays (±15/30/45/60°) whenever that direct line is blocked well short of the goal (§26 — the fix that produced this engagement's first successful B-reach). Hysteresis (§28) persists the previously-chosen detour as an angle offset from the current goal line, not an absolute world direction, specifically so it can't run away the way an absolute-vector version did (goalflight16) — every candidate, including the persisted one, stays structurally capped at the current distance to the real goal.

Two watchdogs, doing different jobs

Lỗi 2's check fires only at a replan boundary: if the spline's own open-loop belief has drifted more than 0.75m from real odometry by the time a new plan is about to start, the start state is re-grounded to reality before planning from it. Lỗi 3's watchdog runs continuously, every 50ms, specifically because a replan boundary can be seconds away — at the incident's own measured divergence rate, real danger builds well within one replan cycle. Its response is a deliberate hold, not a forward replan: a uniform B-spline whose control points are all equal (mathematically constant everywhere), pinned to real odometry — structurally incapable of commanding new motion, which is the whole point when tracking itself is what's failing.

Two guards added this session, both inside the same watchdog path

The executor-stall guard (§29) checks the wall-clock gap since the FSM's own last tick — if the single thread it runs on was descheduled for multiple seconds, it forces a hold rather than trusting a belief that's been running open-loop that whole time. The odom-staleness guard (§31, §36) checks something adjacent but different: whether the position reading being used to build that hold is itself still fresh, since the odom source can independently stall under the same load. Both guards can correctly decline to act — and did, in §36 — which is why the operational discipline of restarting the full planner pair between flights (not carrying a compromised belief across attempts) matters as much as the code itself.

traj_server — a deliberate second process

Fast-Planner publishes its trajectory as a compact B-spline (control points, not a dense path). A separate process, traj_server, subscribes to that, evaluates it at the current wall-clock time on every tick, and publishes a dense PositionCommand for the bridge to consume. Splitting this out means a slow or stalled planning cycle doesn't have to also own the job of continuously re-evaluating and republishing a trajectory that hasn't actually changed — real separation of concerns, and (as §31 found) a real place a stale/duplicate instance can hide if a reset doesn't kill every child process explicitly.

Control and the safety stack

Mechanism

Four independent layers sit between "the planner believes something" and "the vehicle does something dangerous." Tonight is a real demonstration of why that stacking matters — individual layers had real bugs, and none of them became a real disaster alone.

The bridge — the only thing that talks to PX4

fast_planner_bridge subscribes to traj_server's dense PositionCommand and republishes it as PX4 offboard TrajectorySetpoint messages — continuously, at a rate PX4's own offboard mode requires to stay engaged (offboard has its own internal loss-of-setpoint timeout independent of anything this project added). It owns the arm/climb/follow/land state machine described throughout this record: capture home at arm time, climb straight up to hover before ever trusting the planner's own output, hand off to /planning/pos_cmd only once that climb is confirmed complete, and on a clean stop, request AUTO.LAND and wait for a real confirmed disarm rather than just stopping setpoints and hoping.

PX4 itself

PX4's[4] own cascaded controllers (position → velocity → attitude → rate) turn whatever setpoint it receives into actual rotor commands, mixed down individually per motor — in SITL, those commands drive Gazebo's physics plugin directly; on real hardware they'd drive real ESCs. This project never bypasses or replaces any of that — everything upstream only ever hands PX4 a setpoint through its normal, supported offboard interface.

The killswitch — deliberately outside all of it

hard_killswitch.py is a fully separate process that subscribes directly to PX4's own telemetry (not the planner's internal belief about where the vehicle is) and independently checks four bounds every tick: altitude ceiling (8.0m), ground-strike floor (−0.5m), horizontal range (15.0m), and descent rate (1.5 m/s, gated above 1.0m altitude so normal landing descent doesn't trip it). A breach triggers a two-stage response — SIGKILL the bridge first (so no new setpoints can possibly follow), then a direct force-disarm — with the whole breach-to-confirmed-disarm sequence measured at 12-55ms across every real trigger this engagement has produced. It's a separate process specifically so it can't share fate with anything upstream that might itself be stalled, buggy, or compromised — exactly the property that mattered on every real incident this record documents.

Why the stack, not any one layer, is the actual safety story

Search-time pruning and the optimizer's cost terms keep most trajectories safe before they're ever committed to. The FSM's two watchdogs catch divergence between what's commanded and what's real, continuously, without waiting for a replan boundary. Tonight added two more internal guards specifically for data the FSM can no longer trust (a stalled executor, a stalled odom source) — and even when those guards correctly declined to act (§36), the killswitch — reading PX4's own ground truth, sharing no code path with anything that had stalled — was still there. None of these layers is individually sufficient; that's the design, not a gap.

§09Earlier engagement

Kill path — graceful and emergency

Verified

Two tiers, built after a real runaway made the gap between them concrete.

What motivated it

The bridge that relays planner output to PX4 re-requests ARM on every 20Hz control-loop tick whenever it isn't yet armed — necessary for normal startup, but it means an external disarm sent while the bridge is still alive loses that race within about 50ms. A documented 26m runaway incident is what exposed this: the old shutdown path relied on Python's default SIGINT handling, which simply let the process die mid-stream with no attempt to hand control back to the autopilot first.

The fix — two deliberately different tiers

Graceful (the bridge's own state machine): a shutdown signal sets a flag that structurally pre-empts the arm-request branch, requests AUTO.LAND while continuing to hold position (so the offboard-loss failsafe doesn't race the mode switch), stops publishing once AUTO.LAND is confirmed, then waits for disarm with a redundant explicit backstop.

Emergency (the killswitch, a separate process): SIGKILLs the bridge outright, confirms it's actually dead by polling, then force-disarms — for when the bridge itself is the thing that isn't responding, not a case the graceful path can be trusted to handle.

Verification

Both tiers confirmed working in SITL ahead of every flight documented later in this record; the emergency tier's own envelope is covered in full under Cutoff hardening.

§10Earlier engagement

Obstacle-avoidance flights & the occlusion theorem

Foundation

A flight series against real obstacles, and the proof that made receding-horizon planning non-negotiable.

A dedicated series of obstacle-avoidance flights ran during this phase — logs from four separate attempts survive on disk, though the play-by-play of each one doesn't, so this entry stays at the level that's actually verifiable rather than reconstructing detail from memory.

What came out of that series stuck: the occlusion theorem — a goal sitting behind an obstacle is provably unobservable at the moment a mission triggers, since nothing has been seen behind the obstacle yet. A planner that tries to plan directly to such a goal has no choice but to fail or stall. This is the reason receding-horizon planning (frontier of observed space → fly → observe more → replan) became a hard requirement for this project rather than an optimization — Parts 1 and 2 below are what it took to actually build that.

§11Earlier engagement

Start-state exemption

Fixed & verified

The camera's own near-field blind spot was being read as "confirmed empty," when it was really "never looked."

Root cause

Diagnosed as a known structural fact of the depth sensor, not a bug in the map: 0% of the space within 0.3m of the camera is ever actually observed. Anything that treated "unobserved" and "confirmed clear" the same way inside that radius would either refuse to plan at all right where the vehicle already is, or worse, treat unseen space right in front of it as trustworthy.

Fix

A 0.3m exemption radius (esdf_start_state_clearing_radius_m_) around the drone's own position: unconditionally passable, regardless of isObserved(), matching how collision-checking already treated it. This radius later became the shared reference point for the frontier ray-march's own exemption logic (see Receding-horizon, pt. 2).

§12Earlier engagement

Goal-substitution gate

Fixed & verified

A flight that stopped 2.02m short of its real goal — because the planner quietly decided to fly somewhere else instead.

Root cause

checkCollisionCallback's goal-safety check evaluated distance-to-goal without first confirming the goal had actually been observed. Since unobserved space and confirmed-blocked space read as roughly the same near-zero distance, any goal nvblox simply hadn't seen yet looked "too close to an obstacle" — and the code substituted a nearby alternate goal instead, silently, with no error. One real flight was truncated exactly this way, ending 2.02m short of where it was actually supposed to go.

Fix

Gate the substitution on isObserved(end_pt_) as well as the distance check — only substitute when the true goal is confirmed observed and blocked, never when it's merely not-yet-seen. The same isObserved-gating pattern later turned out to be missing from checkTrajCollision too (see Lỗi 1) — this was the first place it was found and fixed, not the last.

§13Earlier engagement

Receding-horizon, part 1 — observed-gated distance

Implemented

The one check everything else in the receding-horizon logic is built on top of.

Before any frontier logic could be trusted, every distance query into the map needed the same discipline: never treat "never observed" as equivalent to "confirmed clear," because the map represents both as roughly the same near-zero value. isObserved(), checked alongside every relevant distance/occupancy query, is the primitive that makes that discipline possible — it's what the start-state exemption, the goal-substitution gate, Lỗi 1's collision gate, and the frontier ray-march below all build on. Foundational, not glamorous: this is the single piece of logic most of this record's other fixes turned out to be a missing instance of.

§14Earlier engagement

Receding-horizon, part 2 — frontier ray-march

Implemented & proven

The actual mechanism: plan to what's been seen, not to what's wanted.

How it works

Each planning cycle first checks whether the true goal is both observed and clear (isObserved(end_pt_) && getDistance(end_pt_) > 0.3) — if so, pass straight through to it, no detour needed. If not, ray-march from the vehicle toward the goal in small steps, stopping at the first point that's neither within the start-state exemption radius nor confirmed observed-and-free. That boundary, pulled back by one step for margin and floored at the exemption radius, becomes this cycle's actual target — recomputed fresh every cycle, never cached, so it can't go stale.

Result

This is the mechanism, later confirmed live: the frontier reliably advances as more space is observed, and the planner reaches a far 8m goal that pure global planning — tried first, under the occlusion theorem's exact failure mode — could never reach at all.

§15Earlier engagement

Bug #2 — the empty-spline crash

Fixed & verified

A real SIGABRT, traced to a state transition that was never supposed to be reachable.

Root cause

checkCollisionCallback's "goal near collision, keep retrying" branch used to force a transition into REPLAN_TRAJ unconditionally — unlike the other two branches in the same function, which were already gated on exec_state_ == EXEC_TRAJ. REPLAN_TRAJ unconditionally evaluates local_data_.position_traj_, which is only valid once a plan has actually succeeded. If this branch fired while still in GEN_NEW_TRAJ — exactly what happens when the goal itself sits in unobserved space, so the branch fires every 50ms with nothing better to switch to — position_traj_ is still a default-constructed, empty NonUniformBspline. Evaluating it indexes into empty control-point and knot arrays, hitting an Eigen out-of-bounds assertion and crashing the whole node.

Fix

Gated this branch the same way the other two already were: only force REPLAN_TRAJ when actually in EXEC_TRAJ. When not, GEN_NEW_TRAJ's own retry loop (with its own backoff) was already retrying toward the same goal regardless — the extra forced transition was never load-bearing for that retry behavior, only for the crash.

§24This session

Combined thrust-vector budget

Implemented & verified

§23 diagnosed a real physical ceiling. This is what it took to actually plan inside it — and the fix that turned out not to be the fix, honestly reported.

The physics

The planner's existing limits were independent per-axis bounds on velocity and acceleration — nothing coupled the horizontal command to how much thrust was left over for vertical. The real constraint a quadrotor faces is a single combined budget: required specific thrust equals commanded acceleration plus gravity compensation, and the airframe only has so much of it — ‖a_cmd + g·ẑ‖ ≤ thrust_ceiling. The ceiling itself came from real telemetry, not a guess: hover_thrust_estimate measured ≈0.7465 for this exact airframe, giving max specific thrust = g / hover_thrust ≈ 13.14 m·s⁻² (thrust-to-weight ≈1.34) — a 20% margin below that became thrust_accel_limit_ = 12.5 m·s⁻².

Three places it had to land, all sharing one number

A single limit isn't enough if only one stage of the pipeline enforces it — the other stages will just reshape the trajectory back past the budget. Search (kinodynamic_astar.cpp): prune any acceleration primitive whose combined thrust exceeds the limit before it's ever expanded. Reallocation (non_uniform_bspline.cpp): when a trajectory still violates the budget after optimization, stretch its time allocation — the old formula (sqrt(violation/limit), valid for pure per-axis acceleration) systematically under-stretched here, because gravity compensation is a fixed offset that doesn't shrink under time-stretching the way the acceleration term does; replaced with an exact closed-form quadratic solve. Optimization (bspline_optimizer.cpp): a coupled cost term with a correctly-derived analytic gradient, so the continuous optimizer stops reshaping search's already-valid output back past the same limit.

The honest negative result

The exact-ratio fix, verified correct in isolation against a standalone synthetic test, made no measurable difference on the next real flight — reallocation ratios sat at ≈1.75–1.9 before and after. Raising the reallocation iteration cap from 3 to 8 didn't fix it either; ratios climbed as high as 1.75, the wrong direction. Neither guess was wrong to try, and neither was the actual answer.

What actually broke the stall: limit_ratio_ — the per-iteration cap on how far each reallocation step is allowed to stretch a single knot interval — was 1.1, conservatively small to avoid overcorrecting any one interval. Raised to 1.3, the very next flight went from 58 rejected replans to zero. The earlier fixes were still necessary (mathematically correct, closing a real under-estimation bug) — they just weren't sufficient on their own, and no amount of iterating on them alone would have found this.

Result

The first flight of this record where the drone actually reached B.

Frontier hysteresis — two bugs, caught in sequence

Fixed & verified

The fan in §26 fixed the collisions. It also, on its own, turned out to be capable of two entirely new failure modes — both found live, both fixed the same session.

Bug one — the flip

The fan re-evaluates every candidate from scratch on every cycle, with no memory of what it chose last time. Two replan cycles seven seconds apart, with real forward progress between them, picked frontier targets 5.8m apart in x — a full reversal from a left-side detour to a right-side one, because the map had updated just enough to nudge which candidate's clearance edged out the other by a hair. The FSM commanded that reversal as a real setpoint change; the vehicle couldn't track it and lost altitude control.

Fix, take one: persist the chosen direction and require a genuinely better candidate — not a marginal one — before abandoning it.

Bug two — the fix's own runaway

Persisting an absolute world-frame direction vector, re-marched from an ever-moving position, has no anchor back to the goal: the reachable distance is capped at the current distance-to-goal, and that cap grows every cycle the vehicle keeps moving along the same fixed direction. Caught live: the frontier target walked from y=8 out to y=12.4, real distance-from-origin climbing straight toward the killswitch's 15m horizontal limit — caught there, safely, but not by design.

Fix, take two: persist the angle offset from the current direct-to-goal line instead of an absolute vector, rebuilding the actual candidate direction fresh from the live goal-line every cycle. Structurally capped at distance-to-goal like every other candidate now, and rotates back toward the goal as the vehicle approaches it — the same behavior the un-persisted fan already had, with a preference for staying on the previously-committed side layered on top, not a new failure mode.

Result

Verified on the next flight: no left-right flips, and — separately, months of drift-margin work paying off — a real 0.75m-margin near-miss on pillar_03 mid-flight that the vehicle recovered from on its own and still reached B.

The executor-stall discovery

Real crash mechanism found

A crash that looked, from a distance, like more of the same collision pattern. It wasn't near any obstacle at all.

What the raw log showed

A flight crashed with a signature seen twice before and dismissed as recoverable transients: the commanded target barely moving while the real vehicle's position jumped and altitude collapsed. This time it happened at a position roughly 1.7m from the origin — nowhere near pillar_03, before the vehicle had even reached the obstacle ring. The raw console log across the crash window showed a 4-second stretch with zero log lines from the planner node — not one slow callback, a complete blackout.

Root cause

fast_planner_node is single-threaded (rclcpp::spin() — every timer, every callback, on one thread). Under real system load, the process itself was getting descheduled for multi-second stretches. During the gap, the commanded spline kept advancing in wall-clock time — its position is evaluated as t_cur = now() − start_time_, regardless of whether anything actually ticked — while the real vehicle didn't move. By the time processing resumed, the existing re-ground safety check (§18) correctly caught a 3.36m divergence and snapped the belief back to reality — but the "catch-up" trajectory computed immediately after was itself built from an already-compromised situation, and roughly 2.3 seconds later real divergence hit 8.877m: the vehicle was already on the ground.

This reframes the two earlier "recoverable transient" events (§28) as the same mechanism, observed twice more — one recovered by luck of timing, one didn't.

Fix

An executor-stall guard at the top of the FSM's own tick: if the wall-clock gap since the last tick exceeds 0.3s (30× the nominal 10ms period — comfortably clear of ordinary jitter, small next to the multi-second blackouts that actually caused damage), immediately publish a hold pinned to real odometry before trusting anything the stale open-loop belief would compute — instead of waiting for a position-divergence symptom to grow large enough to trip the existing watchdog after the fact.

Validated under real, worse-than-ideal conditions — not a synthetic test: across two flights, 200+ genuine stall events logged (2.3–4.8 seconds each, driven by real sustained system load, not injected). Zero crashes. Every single one caught and held safely.

Result, honestly qualified

Some of what remains is outside this project's reach entirely: an unrelated host process (a cloud-storage sync client) was caught independently spiking to 125% CPU mid-session. §31This session

The odom-staleness crashes

Fixed & verified

Two crashes in a row, both at the exact same instant — the climb-to-follow handoff — neither one an obstacle collision.

What happened

A live re-test climbed cleanly to hover, then immediately commanded a near-ground target the instant it switched from climb to Fast-Planner following — target altitude 0.53m against a real altitude of 4.75m. The bridge tried to descend fast enough to close that gap; the killswitch's descent-rate guard correctly caught it (1.52 m/s > 1.5 m/s limit) and force-disarmed in ~30ms — but disarming 4.4m up meant a free-fall to the ground in SITL. It happened again on the very next attempt.

Root cause

triggerTrackingDivergenceHold() — the Lỗi 3 watchdog's safety hold, and the executor-stall guard's own fallback — pins its hold trajectory to odom_pos_ unconditionally, trusting it as "real position, right now." Nothing tracked how OLD that reading was. The odom SOURCE (ground_truth_tf) can itself get starved under the same host-load pressure the stall guard exists to handle; when it does, odom_pos_ keeps holding whatever position was last received — in this case, a reading from ~6 seconds earlier, still near the ground from partway through the climb. The hold pinned to that phantom position, and everything downstream treated it as ground truth.

Fix

Track wall-clock receipt time in odometryCallback(). Before triggerTrackingDivergenceHold() commits to odom_pos_, check its age against a 0.5s staleness limit — if it's too old, skip publishing entirely rather than guess, leaving whatever trajectory is already active untouched. A close relative of the executor-stall guard (§29): don't act on a reading you can no longer vouch for.

Verified live, in the log: the very next re-test hit the identical stall pattern the odom source has always been vulnerable to — and this time, instead of pinning to a phantom position, it logged ODOM STALENESS GUARD: skipping tracking-divergence hold -- last odom received 4.456s ago and did nothing, correctly. The vehicle held safely at altitude instead of crashing a third time.

A second bug found during cleanup

The second crash turned out to have a compounding cause: killing the old launch wrapper between attempts didn't cascade to its already-spawned traj_server child process (SIGKILL to a parent doesn't kill orphaned children), leaving two independent traj_server instances publishing to the same /planning/pos_cmd topic — the bridge was racing between a fresh planner's real output and a stale process's leftover state. Fixed by explicitly killing every child process by PID during any reset, not just the launch wrapper.

§32This session

The livelock, under real load

Root cause found, not yet closed

With the crash fixed, the next re-test didn't crash — it just never went anywhere.

What happened

The vehicle climbed, planned once successfully, and then sat parked barely past the start point for 44 minutes straight, completely safe, never progressing. 126 executor stalls logged over that window — roughly one every 15-20 seconds on average, though sometimes back-to-back every 2-4 seconds.

Audited 2026-08-28: the surviving log for this exact window (fast_planner_relaunch.log, the FSM's last transition into EXEC_TRAJ to end of file) shows 336 EXECUTOR STALL warnings, not 126 — every one of them after that last transition, consistent with the livelock story itself, just a higher raw count than what was recorded live at the time. No alternate counting rule (a duration cutoff, deduplication by second, etc.) was found that reconciles the two numbers. The 126 figure is left here as originally recorded rather than silently replaced; treat the log's 336 as the more trustworthy count if the exact number matters.

Root cause: the stall guard's own success condition, working against itself

The §29 executor-stall guard returns immediately, every time it fires, before the FSM's normal switch-statement logic — the code that would otherwise notice "this trajectory is finished, time to replan toward the real goal" — ever gets to run. Under light load that's fine: stalls are rare, so plenty of ticks fall through to the real logic between them. Under sustained load, if stalls recur faster than the guard's own hold-and-cooldown cycle can clear, the FSM can get stuck ping-ponging between "stall detected, hold" and "next tick, still stalled, hold again" indefinitely — a genuine livelock. Confirmed directly in the FSM's own transition log: WAIT_TARGET → GEN_NEW_TRAJ → EXEC_TRAJ once, then nothing for 44 minutes.

A full container restart (clearing 77 accumulated zombie processes and dropping host load from 10+ to 3-5) helped, but wasn't sufficient on its own — a follow-up re-test still hit the same pattern at a merely moderate load of 3-5, plateauing after making some real progress instead of none. The livelock's trigger threshold is lower than "heavily loaded"; even "somewhat loaded" is enough.

Not a regression, and not fixed by a restart: this is the same "safe but slow under load" limitation documented in §30 and Status at a glance, just observed for the first time in its most severe form — full livelock rather than partial slowdown. The fix isn't operational (restart, close the GUI); it's architectural. See §33.

§33This session

Multi-threading, tried & reverted

Attempted, found a worse bug, reverted

The structural fix for §32 — and an honest account of why it isn't in place tonight.

The change

fast_planner_node ran rclcpp::spin(node) — a single-threaded executor — since the very first line of this project. Every timer and subscription, control and map alike, serialized on one thread by construction; that's the root architectural cause behind both the executor-stall pattern (§29) and the livelock it can produce (§32). The fix: split flight-control work (exec_timer_, safety_timer_, odom/waypoint subscriptions) and map work (vis_timer_, the two ESDF fetch timers, the nvblox service client) into two separate ROS callback groups, and run them under a MultiThreadedExecutor instead — so heavy map population can no longer block the 10ms control tick, regardless of host load.

It worked, for what it targeted

The very next test flight logged zero executor stalls, versus 100+ in the flight before it. The specific failure mode in §29/§32 was gone.

It also broke something new

The kinodynamic search started failing almost every attempt — including a trivial ~0.3m hop in completely open space, nowhere near any obstacle (logged: start=(0.06,0.28,5) → goal=(0.06,0.58,5), kinodynamic search fail!, repeatedly). Root cause: SDFMap's buffers are plain vectors, written in-place by the map thread with no synchronization against concurrent reads from the now-separate search thread. Fixed-size, no reallocation, so this can't crash the process — but it can hand the search a read caught mid-update, e.g. a just-recentered local_bound_ region whose voxels haven't been refilled yet, defaulting back to "occupied" under the project's own unknown→occupied policy at exactly the moment the search reads them.

Reverted the same night. A search that fails almost every attempt is a worse failure than a livelock that at least holds safely — nothing would ever fly, even under zero load. This is a genuine, newly-introduced concurrency bug, not something to leave running on flight-safety-relevant code while iterating live under time pressure. Reverted fast_planner_node.cpp back to the single-threaded executor; the two callback groups are left wired up elsewhere (inert, harmless, under a single-threaded executor) so a future attempt with proper synchronization around SDFMap's buffers doesn't have to redo that plumbing.

What this means going forward

The livelock in §32 is still open. Closing it for real needs the multi-threaded executor plus real synchronization on the shared map state — a double-buffer swap or an explicit lock around the read/write path — designed and tested deliberately, not attempted live in the middle of a demo flight.

§34This session

Optimizing for the Jetson, not just this box

Applied & verified

A pointed reminder: this dev box is more powerful than the Jetson Orin Nano the real drone will fly on. If it's straining here, it needs to be cheaper, not just less contended.

Fix one — stop paying for viewers that aren't there

None of the five visCallback() publish functions checked whether anyone was actually subscribed before doing their full local_bound_min_..max_ voxel iteration (~1.09M voxels each). Two of the five — /sdf_map/occupancy and /sdf_map/esdf — turned out to have zero consumers anywhere in this project's own viewing setup (confirmed against the RViz config directly), so they'd been iterating a million-plus voxels every cycle for nobody, unconditionally, the whole engagement. Added a subscriber-count check to the top of all five: each one now early-returns instantly when nothing's listening, and publishes at full fidelity the instant something subscribes. On a real Jetson flight — headless, no RViz2 open mid-mission — this collapses roughly 5.5M voxel visits per 500ms cycle down to five cheap integer comparisons. Verified both directions live: /sdf_map/occupancy confirmed 0 subscribers → 0 published messages; /sdf_map/occupancy_inflate confirmed publishing normally the instant something subscribed.

Fix two — stop recomputing the same address three times

The corridor ESDF fetch's inner min-pooling loop rebuilt the flat array address sx*ny*nz + sy*nz + sz from scratch on every single (ix,iy,iz) triple, even though the sx*ny*nz and sy*nz terms don't change until their own loop variable changes. Hoisted both to the loop level they're actually invariant at — a pure algebraic restatement, not a behavior change (sx*ny*nz + sy*nz + sz is exactly sx_off + sy_off + sz for every voxel). This is the single most expensive required — non-visualization — callback in the whole system, run against ~2.1M destination voxels on the corridor tier alone; a per-Jetson-core FP/integer throughput deficit hits this one harder than almost anything else in the pipeline.

Measured, not assumed: corridor-fetch callback time dropped from 184–232ms (the last documented baseline, §30) to 104–120ms — roughly a 40–45% reduction — from the address hoist alone, verified against live DEBUG_TIMING log output on this same dev box. Correctness verified separately via the existing debug-query mechanism: a known point returned the same sane, correct isObserved/distance_buffer_all_/getInflateOccupancy values before and after.

What this doesn't claim

Neither fix touches the livelock in §32/§33 directly — reducing map-population cost doesn't add concurrency, so a sufficiently loaded single thread can still starve. What it does do: lowers the total work competing for that one thread in the first place, which is the more foundational lever, and one that helps unconditionally, on this box tonight and on the actual target hardware later, independent of whichever executor model eventually wins.

Conclusion

Where this leaves the project, stated plainly.

The core navigation capability is proven, repeatedly, in simulation: a multicopter reaches a goal 8m away with a real obstacle ring directly in its path, ten separate times across this record, using nothing but a depth camera's ESDF and a kinodynamic planner to find its way around what it can't yet see — currently flying on PX4's GPS-fused pose as a deliberate Milestone-1 stand-in for the vision estimate that will eventually replace it. The receding-horizon frontier this required, the combined thrust-vector budget that made the resulting trajectories flyable, and the four-layer safety stack that caught every real divergence this record produced — including twice as the sole reason a real problem didn't become a real crash — are all implemented, tested under genuine load, and documented down to the mechanism level in Part I.

What isn't proven yet is the harder half of the original mission statement. Milestone 2 — cuVSLAM actually driving control, GPS removed for real — hasn't started; the GPU-contention drift that forced the fallback to GPS in the first place is still unsolved, not just deferred. The executor livelock is understood architecturally (§32) but not closed: the fix that would close it (a multi-threaded executor with real synchronization on the shared map state) was built, found a worse bug, and was reverted the same night, leaving "safe but occasionally stuck" as the honest current ceiling rather than "reliably fast." And nothing in this document has flown on real hardware — every result, every number, every fix is SITL.

None of that is hidden in the sections above, and it isn't hidden here either. The next real step is narrow and specific, not a vague "more testing": add proper synchronization to SDFMap's shared buffers and re-attempt the multi-threaded executor deliberately, then re-open Milestone 2 once that foundation is solid. Everything else documented in Open Issues (§39) is either already mitigated, already scoped as future work on the actual Jetson hardware, or — per the discussion above — a documentation lesson about keeping the record as honest as the system it describes.

TSDF
Truncated signed distance field — nvblox's intermediate representation, built directly from depth-image ray fusion within a narrow band around each observed surface; the ESDF is propagated out from it.
Motion primitive
One short, dynamically-feasible segment (a fixed acceleration integrated over a time step) the kinodynamic search expands from — every search node is a state the vehicle could actually fly to, not just a geometrically reachable cell.
Min-pooling
Taking the minimum (not average) value over a covering block when downsampling to a coarser resolution — the conservative choice for a safety distance field, since it never overstates clearance.
VIO
Visual-inertial odometry — fusing camera and IMU data into a single drift-resistant motion estimate; cuVSLAM's role in this architecture.
Frontier
The boundary of currently-observed free space; the receding-horizon planner's actual per-cycle target, not the true mission goal.
EXEC_TRAJ / REPLAN_TRAJ
Planner FSM states: actively executing a trajectory, versus computing its replacement.
Killswitch
An independent process outside the planner that monitors PX4's own estimate directly and force-disarms on any bound breach.
SITL
Software-in-the-loop — PX4 running against a simulated airframe, here paired with full Gazebo perception.
Confirmed-obstacle
The intersection of "observed" and "occupied" — the one map signal that actually proves the camera verified something solid is there, as opposed to space merely not yet seen (which reads the same as occupied under this project's unknown→occupied policy).
Executor stall
A wall-clock gap in the planner's own control-loop ticking, caused by the single thread it runs on getting descheduled under system load — not a bad planning decision, a decision computed from stale time.
Hysteresis (frontier)
Persisting the previously-chosen detour angle across replan cycles, and requiring a clearly better alternative before abandoning it — added after the un-persisted fan flip-flopped between left and right detours cycle to cycle.
Corridor / near tier
The two ESDF fetch ranges SDFMap pulls from nvblox: a fast, small near-field fetch immediate avoidance depends on, and a slower, much larger corridor fetch for longer-range look-ahead.
local_bound_min_ / local_bound_max_
The 3D voxel-index range every map-visualization publisher iterates. Left at its zero-default for the whole engagement until §27's fix recentered it on the drone's live position.
Livelock
A safe-but-permanently-stuck state: the process keeps running and never crashes, but a self-reinforcing pattern (here, the stall guard's own early-return) prevents it from ever reaching the logic that would make forward progress.
Callback group
A ROS 2[5] grouping mechanism that determines which callbacks are allowed to run concurrently under a multi-threaded executor; callbacks in the same group never overlap each other, callbacks in different groups can run on different threads at once.
MultiThreadedExecutor
A ROS 2 executor that spins multiple threads instead of one, allowing callbacks in different callback groups to run concurrently — the structural fix attempted in §33.
Subscriber-count gating
Checking a publisher's get_subscription_count() before doing the (potentially expensive) work of building its message, and skipping entirely if nobody's listening — applied to all five map-visualization publishers in §34.
Home capture
The bridge's arm-time behavior of setting its climb reference to wherever the vehicle physically is at that moment, not a fixed world origin — a landed-in-place drone re-armed without a world reset silently starts its next mission from the wrong point (§35).
